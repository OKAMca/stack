# Wysiwyg Block

<Description of={WysiwygStories} />

#### Wysiwyg Block. Can be used in CMS to insert HTML elements as text with certain attributes (h1, h2, h3, link with target, etc.)

`WysiwygBlock` has no `'use client'` directive: render it from a Server Component and the HTML is
sanitized on the server, so `sanitize-html` never reaches the browser bundle. Importing it from a
client module still works, but then the sanitizer ships to the client.

## Sanitizing before caching and serialization

For server applications, sanitize HTML where data enters the application. Store and
serialize the returned `SanitizedHtml` string. Import the rendering component from
`@okam/stack-ui/wysiwyg` in server or client components:

```tsx
// Server data loader
import { sanitizeWysiwygContent } from '@okam/stack-ui/wysiwyg/server'
const content = sanitizeWysiwygContent(cms.content)

// Server or client view
import { WysiwygBlock } from '@okam/stack-ui/wysiwyg'
<WysiwygBlock content={content} />
```

The server entry requires a server environment supporting `server-only`. Its defaults
omit inline styles and embedded frames. Supply `allowedStyles` and
`allowedIframeHostnames` for the content your application accepts. Tag and attribute
options belong at the data boundary. Keep application field mappings and cache
invalidation alongside that policy. The brand records sanitization in TypeScript;
validate external data before assigning it the generated result type.

The root `@okam/stack-ui` export remains compatible with raw strings and existing
options, including client-only applications. It sanitizes at render time. When
imported by a client component, it includes the sanitizer in the browser bundle.
The `wysiwyg` entry renders only and has no sanitizer dependency. Both entries use
the same Typography rendering implementation.
